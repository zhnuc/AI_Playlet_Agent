# 角色卡与角色历史方案

最新修改：2026-04-17 21:10

说明：面向前端与协作同学的可交付方案文档，用于统一角色卡、角色历史查看和聊天记录浏览链路的页面结构与交互口径。

## 1. 目标

本模块的目标不是重新设计“角色生成”，而是围绕多角色 Agent 对话，为每个角色提供一个可查看的“角色详情与历史记录”入口。
整体交互参考 QQ / 微信聊天界面的使用直觉，但不照搬其视觉样式。

本模块要解决的核心问题：

- 用户如何快速进入某个角色的详情
- 用户如何看到角色的基础信息
- 用户如何回看该角色在剧情中的历史发言
- 用户如何按集数、关键词、时间顺序筛选

## 2. 当前项目里的可复用基础

当前前端已经存在：

- 阶段 1 的角色选择卡片和角色设计器
- 阶段 3 的群聊式推演沙盒
- `chatFeed` 消息流

当前缺少：

- 角色详情面板或抽屉
- 角色历史检索面板
- 从角色头像 / 名字跳转到详情的统一入口

因此，本模块更适合在现有界面基础上补一个详情面板，而不是另起一套独立页面。

## 3. 用户任务

### 3.1 查看角色详情

用户点击某个角色头像、名字或角色卡后，应能打开该角色的详情面板。

### 3.2 回看角色发言

用户希望查看：

- 某个角色在第几集说过什么
- 在哪些轮次、哪些场景说过什么
- 这些发言按时间顺序如何串联

### 3.3 快速检索

用户希望支持：

- 按集数筛选
- 按关键词搜索
- 按时间顺序查看

扩展项：

- 查看该角色与某个对象之间的互动片段

## 4. 建议的界面结构

## 4.1 入口

建议优先支持以下入口：

- 阶段 3 聊天流中点击角色头像

统一原则：

- 当前首版只保留这一种主入口，不扩展为多入口体系
- 每条角色消息应带头像和名称
- 点击头像进入该角色的详情视图

## 4.2 形态调整

当前已不采用右侧抽屉方案。

首版只保留：

- 从群聊 UI 中点击角色头像进入角色卡

角色卡的最终承载形态仍待进一步确认，但当前已经排除：

- 右侧抽屉
- “当前对话角色列表”统一入口

当前已进一步明确为两层结构：

- 第一层：居中的角色卡弹窗
- 第二层：更大的“聊天记录”历史窗口

职责划分：

- 角色卡弹窗负责快速查看“这个角色是谁，以及他/她在当前集刚刚说了什么”
- 历史窗口负责查看该角色跨历史会话的完整聊天记录

## 4.3 面板分区

建议分为两个主区：

### A. 角色信息

展示：

- 姓名
- 性别
- 年龄
- 身份
- 外观标签
- 性格标签

当前进一步收敛为：

- 顶部信息区不额外加入“当前剧情关系摘要”
- 标签区同时容纳：
  - 静态标签
  - 动态标签

动态标签可承载：

- 当前情绪
- 当前立场
- 当前冲突对象

### B. 历史记录

展示：

- 发言时间线
- 第几集
- 场景
- turn / step
- 发言内容
- 发言类型
  - `dialogue`
  - `action`
  - `thought`
  - 当前首版即展示三种类型

## 4.4 阶段 1 角色卡展示规则

当前已明确：

- 阶段 1 主页面角色区展示“全部角色卡”，不再只显示核心角色。
- 当角色卡数量超过 3 张时：
  - 默认仅显示前 3 张
  - 提供“查看更多（共 N 个角色）”入口
  - 点击后展开显示全部卡片，并支持“收起”

排序建议：

- 仍优先按角色定位优先级排序（男一、女一、大反派等在前）
- 但不因非核心定位而隐藏卡片

## 5. 历史记录的交互建议

## 5.1 默认视图

默认按时间倒序展示一个角色的历史记录列表，即最新在上。

每条记录建议至少包含：

- 集数标识
- 场景名
- turn 编号
- 一小段发言或动作摘要

当前首版进一步收敛为：

- 角色卡主视图只展示当前集前几轮的角色记录
- 不在首屏直接展开跨历史会话的全量聊天
- 默认显示 5 条；如果不足 5 条，则按实际条数展示
- 可继续提供“展开更多”

## 5.2 筛选区

建议在历史区顶部提供：

- 集数筛选器
- 关键词搜索框
- 排序切换
  - 最新在前
  - 最早在前

## 5.3 扩展项

当前优先保留的扩展入口是“聊天记录”。

含义：

- 在角色卡中提供一个“聊天记录”按钮
- 点击后进入该角色的完整历史会话浏览视图
- 用于查看该角色此前所有历史聊天
- 历史窗口默认按“集”分组组织内容
- 每集内部再按时间流展示

完整历史窗口的检索规则当前进一步明确为：

- 搜索范围默认覆盖 `thought / action / dialogue`
- 搜索后不打散原有分组，仍按“集”展示命中结果
- 提供内容类型筛选：
  - `全部`
  - `thought`
  - `action`
  - `dialogue`
- 默认展开当前集，其余集折叠
- 历史记录项优先展示：
  - `集数`
  - `scene`
  - `turn`
  - `kind`

“只看与某角色的互动”仍可保留为后续扩展，但不是当前第一优先项。

## 6. 数据结构建议

## 6.1 角色基础信息

建议前后端统一使用稳定的 `character_id`，不要只依赖角色名。

原因：

- 角色名可能会改
- 前端多个模块需要稳定引用同一角色
- 关系图、角色卡、历史记录都需要用同一个主键

建议结构：

```json
{
  "character_id": "char_linruoxue",
  "name": "林若雪",
  "gender": "女",
  "age": 24,
  "identity": "林家真千金，重生归来",
  "appearance_tags": ["冷艳", "利落", "黑长发"],
  "personality_tags": ["克制", "锋利", "报复心强"]
}
```

## 6.2 历史记录

建议结构：

```json
{
  "character_id": "char_linruoxue",
  "history": [
    {
      "event_id": "evt_00128",
      "episode": 1,
      "scene": "董事会会议室",
      "turn": 5,
      "kind": "dialogue",
      "content": "今天这份协议，我不签。",
      "timestamp_label": "E1-T5"
    }
  ]
}
```

## 6.3 可选扩展字段

如果后续需要支持“只看与某角色互动”，可扩展：

```json
{
  "interaction_partner_ids": ["char_guhanting"]
}
```

但该字段当前不是强制要求。

## 7. 前后端边界

## 7.1 前端负责

- 角色卡入口统一
- 详情面板渲染
- 历史列表渲染
- 集数筛选
- 关键词搜索
- 排序切换

如果是静态原型：

- 这些逻辑都可以先在前端本地完成

## 7.2 后端或中间层理论上需要提供

- 稳定的角色主键 `character_id`
- 角色基础信息
- 可检索的历史记录数组
- 记录与剧情事件的锚点
  - `episode`
  - `scene`
  - `turn`
  - `event_id`

## 7.3 当前项目中的潜在真实来源

未来真实接线时，可优先参考：

- `state.roleDrafts` 对应的角色基础信息
- `GET /sessions/{session_id}/events` 返回的事件流
- runtime snapshot 中的角色与 turn 信息

但本轮文档不要求把这些结构真正打通。

## 8. 原型阶段建议

如果后续要做静态原型，建议：

### 8.1 阶段 3 主消息布局

当前已明确采用“群聊统一左对齐”方案。

含义：

- 所有角色消息都按群聊逻辑统一左对齐
- 通过头像、角色名称、气泡样式区分不同角色
- 不采用双人私聊式左右错落布局

这样更符合“多角色共同演绎”的阅读直觉，也更利于后续把系统消息单独抽离成另一类视觉层。

### 8.1.3 顶部状态栏

当前已明确：

- 原顶部“短剧创作指挥台”压缩为固定悬浮状态栏
- 只保留：
  - `运行模式`
  - `Session`
  - `当前状态`

`当前集 / 当前轮次` 不在该状态栏内重复展示，避免与页面其他区域信息重复。

### 8.1.1 单条角色消息结构

当前已明确采用以下结构：

- 左侧为角色头像
- 头像右侧上方为角色名称
- 名称下方为消息气泡
- 气泡内部按真实时间混排展示 `thought / action / dialogue`
- 每类内容使用标签或弱分隔方式区分，而不是只保留对白

当前暂不设计：

- 点击消息气泡展开额外上下文
- 点击消息体进入角色卡

角色卡入口只保留为“点击头像”。

### 8.1.2 系统消息结构

导演 / 系统 / 监制消息继续独立于角色消息呈现：

- 使用居中提示条或浅色系统卡
- 保留时间或 turn 标记
- 强调其“控制 / 事件提示”属性，而非角色对话属性

### 8.2 非角色消息

当前已明确：

- 导演 / 系统 / 监制消息优先采用居中提示条或浅色系统卡
- 不与角色对话气泡完全同构

这样可以减少系统控制信息对角色演绎阅读节奏的干扰。

### 8.3 头像策略

当前首版方案需要预留真实头像图位。

意味着：

- 首版即便使用占位图，也应保留图片容器结构
- 不只用纯文本首字头像替代
- 角色卡、聊天流、关系图后续都可复用同一头像资源引用

- 在现有前端里补一个角色详情抽屉
- 使用 mock 的角色基础信息
- 使用 mock 的历史记录列表
- 在前端本地实现集数筛选与关键词搜索

原型阶段重点是证明：

- 入口合理
- 信息结构清楚
- 用户能理解怎么找历史

## 9. 验收标准

本模块的方案验收标准为：

- 角色卡入口清晰
- 基础信息与历史记录边界清晰
- 集数筛选、关键词搜索、时间顺序查看的逻辑清晰
- 前后端边界可直接交给同学继续开发
- 方案不再混入“角色生成”作为主目标
