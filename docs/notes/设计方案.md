五、核心争论：多智能体对话调度机制

这是本次会议最长、最激烈的讨论焦点。

问题场景
A（妈妈）同时对B（大儿子）、C（小儿子）说："你们在干嘛？"

方案对比


方案一：单链线性
方案二：并发多指向
next_speaker
只指定1人
可指定多人（列表）
流程
A→B→C→A（严格顺序）
A同时→B和C，B/C各自响应
优点
简单可控，不会指数发散
更真实，不会遗漏角色
缺点
C会被B的发言"带偏"，不回答A的问题；B可能把next_speaker指回A，把C晾在一边
可能分支发散（2^n），输出混乱，实现复杂

最终达成的共识方向

经过反复争论，会后文字讨论达成了更明确的共识：

next_speaker：一个列表字段，可包含单个或多个角色名

规则设计：

1. 常态：next_speaker指定1人，单链互动
2. 群发时（next_speaker含多人）：
  - B、C等被指定者必须回复A（发起者），不能B、C之间先互动
  - 回复完毕后，选择权交还A，由A决定继续群聊还是单独聊
3. "不说话"的表达：
  - dialogue / action / inner_thought 均可为none
  - 三个字段全为none = 不回复，不写入global_history
  - 但agent至少应产生inner_thought（王子文认为三个维度都没想法不现实）
4. 防发散机制：
  - 提示词设计上引导agent尽量单人互动，偶尔群发
  - 可加阈值：超过6个会话数强行截断，不再增长会话

七、用户干预机制

回退（Rollback）
- 用户选择撤销N步，global_history截断到对应位置
- 类似DeepSeek网页端的历史记录回退（砍掉后面的对话）
  
用户反馈（Temporary Feedback）
- 回退时可同时提交意见（"上帝指令"）
- 该指令注入history中，仅对下一次agent调用生效
- 生效后立即抹除，不污染global_history的JSON结构
- 用户也可只回退不提意见
  
结束控制
- 角色agent可输出next_speaker: "end"表达想结束本集的意愿
- "end"不代表真正结束，需经过：
  - 监制agent判断 / 用户最终决策
  - 用户权限 > 监制agent权限
    
监制Agent介入（设想中，未实现）
- 在特定step（如第4、8、12步）自动调用
- 可发出指令：cut / continue / 剧情加快 等
- 监制指令可保留在全局history中持续生效（与用户临时指令不同）
  
1. [底层多智能体推演参考] THU-KEG / StoryWriter
  - 特点：清华大学开源的多智能体长文本生成框架。其包含大纲 Agent、规划 Agent 和写作 Agent。
  - 借鉴点：直接提取其“动态上下文压缩（Memory 截断）”和“大纲生成策略”的底层逻辑，用到我们的“阶段二：剧情路由与骨架生成”中。
2. [沙盒与角色扮演参考] multi-agent-story-generation (MARP)
  - 特点：基于多智能体协作和角色扮演的故事生成框架，内置了全局设计师、场景设计师、角色控制台等 Agent。
  - 借鉴点：它的“状态机”和“角色对话机制”可以直接作为我们“阶段三：多智能体推演沙盒”的核心引擎基础代码。
3. [商业化端到端参考] chatfire-AI / huobao-drama (火宝短剧)
  - 特点：基于 AI 的一站式短剧生成平台，涵盖从一句话生成剧本、提取角色到最终成片的完整全自动工作流。
  - 借鉴点：借鉴其对外的 API 接口设计以及提示词结构，尤其是它如何将复杂的剧本格式清洗为标准分镜剧本。
4. [前端 UI 交互参考] ponysb / 91Writing 或 LobeChat
  - 特点：优秀的 Vue3/React AI 写作与对话前端项目。
  - 借鉴点：拆解其前端的流式输出（SSE）打字机效果、角色卡片管理以及富文本编辑器，用于构建我们的“导演控制台”。

一、 敏捷开发三步（滑板 ➔ 自行车 ➔ 汽车）

核心原则：每个迭代结束时，必须有一个能跑通演示（Demo）的版本，绝不把风险留到最后一天。

🛹 V1.0 滑板期：单轨直通车（目标：实现“常规创作模式”）
- 产品形态：用户输入标签 ➔ 系统生成大纲 ➔ 系统直接生成剧本。没有沙盒，没有多智能体对话。
- 技术实现：完全依赖 Coze Workflow（工作流）。将标签解析、大纲生成、剧本排版串联成一个 Coze 工作流。后端只需透传 Coze API，前端展示最终结果。
- 价值：验证前后端链路打通，保证项目有最基础的“保底作品”。
  
🚲 V2.0 自行车期：自动推演沙盒（目标：实现“自由创作模式”的自动播报）
- 产品形态：用户确认大纲后 ➔ 角色A 和 角色B 开始在界面上自动聊天 ➔ 聊完后生成剧本。
- 技术实现：引入 Coze Bot（智能体）。后端作为“聊天室群主”，调用 Coze API 将 A 的话发给 B，再把 B 的话发给 A。前端以聊天记录形式展示推演过程。
- 价值：实现多智能体（Multi-Agent）核心卖点，系统具备观赏性。
  
🚗 V3.0 汽车期：人类导演控制台（目标：完整满血版）
- 产品形态：沙盒推演中途，前端实现 SSE 打字机效果。人类可以随时点【暂停】，输入【天降陨石】，角色根据新指令继续演。同时后台“监制 Agent”静默巡检，发现水字数自动切断。
- 技术实现：后端挂载复杂状态机，接管 Coze 的流式输出（Stream）。增加监制检测机制和指令强插逻辑。

针对 Coze API 的防踩坑指南（必看）：
1. 超时问题 (Timeout)：Coze 的 Workflow 有时候运行极慢（尤其是大纲生成阶段可能长达 30 秒 - 1 分钟）。前端务必做好长文本 Loading 动画或步骤提示（“正在构思世界观...”、“正在分配角色...”），不要让用户以为死机了。
2. Bot 隔离原则：在 Coze 上建 Bot 时，给“角色A”和“角色B”分别建立独立的 Bot，而不是把他们塞进一个 Bot 里。这样后端在调度时，只需交替调用两个 Bot 的 API，状态最清晰，绝不会串戏。
3. 记忆 Token 爆炸：如果角色互聊超过 20 轮，Token 成本极高且极易触发限制。后端 P3 必须写一个滑动窗口策略：每次调 Coze API 时，只带上最近 5 轮的聊天记录，外加最初的系统大纲即可。

极速开发技术栈清单（“快、稳、炫”选型）
既然只有 18 天，千万不要用过于沉重或冷门的技术。以下这套组合是目前开发 AI Web 应用（AI Agent 平台）最主流、开源组件最多的“黄金搭档”：
1. 前端技术栈 (Frontend) —— 主攻：流式渲染与炫酷交互
- 核心框架：React (Next.js) 或 Vue 3 (Nuxt.js)。（看前端同学哪个更熟，推荐 Next.js，因为 AI 相关的开源 UI 组件库多基于 React）。
- UI 组件库：Shadcn/ui 或 Ant Design / Element Plus。（强烈推荐 Shadcn/ui，极简黑客风，高度可定制，特别适合做控制台界面）。
- CSS 框架：Tailwind CSS（不用写冗长的 CSS 文件，直接在 HTML 里写原子类，开发速度提升 300%）。
- 流式请求库：@microsoft/fetch-event-source（完美解决前端接收大模型打字机 SSE 流的问题，原生 fetch 处理流极其痛苦，直接用这个库）。
- 动画库 (选加)：Framer Motion（给“人类导演干预”面板加一点弹出的阻尼动画，评委看起来会觉得非常高级）。
2. 后端技术栈 (Backend) —— 主攻：高并发调度与接口防抖
- 核心框架：Python FastAPI（处理 AI 请求、大并发、异步流式输出绝对的王者，比 Java/Spring Boot 轻量，比 Node.js 算力更优）。
- 网络请求：HTTPX（Python 的异步请求库，用于高频调用 Coze API，防止后端阻塞死锁）。
- 数据验证：Pydantic（FastAPI 自带，严格校验前端传来的 JSON 和 Coze 返回的 JSON 格式，防止大模型幻觉导致系统崩溃）。
3. 数据库与存储 (Database) —— 主攻：极简与快速回档
- 关系型数据库：PostgreSQL 或 MySQL（存储用户账号、项目剧本、历史存档）。
- 内存数据库：Redis（必选！必选！）。多智能体在沙盒里聊天时，必须用 Redis 暂存他们最近 5 轮的对话上下文（滑动窗口机制），如果存 MySQL 读写太慢，如果放内存极易丢失。
4. 部署与基建 (DevOps) —— 主攻：一键上线、公网展示
- 前端部署：Vercel（绑定 GitHub，代码推上去自动发布，自带 HTTPS，免费且对 Next.js 支持完美）。
- 后端/DB 部署：Zeabur 或 Railway 或 轻量级云服务器（腾讯云/阿里云/百度云）+ Docker。
